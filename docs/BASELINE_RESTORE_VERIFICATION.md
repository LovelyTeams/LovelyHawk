# 基线历史恢复的验证范围

此文说明 core 的基线历史恢复能力。桌面“配置 → 检查这台主机 → 变更历史”现已为可写单项基线（不含 Nginx、Redis、PostgreSQL）的新记录提供“放回改动前的文件…”，经计划、应用内确认、执行和独立读回完成，流程与容器验证见 `BASELINE_CHANGE_VERIFICATION.md`。下面的 Redis 恢复样例仍只是 core 实验，不能计为桌面修补验收。

## 可执行的恢复计划

新基线变更记录完整文件的修改前备份摘要，以及修改后的 SHA-256、权限、UID/GID、设备号、inode 和链接数。恢复计划绑定这份记录、目标与本次确认；执行前重新核对历史状态，拒绝已经恢复或发生变化的记录。恢复的是明确列出的完整文件，不能把某个键的旧值当成整份文件未变化的证明。

所有目标文件和备份先通过检查，再开始写入。当前文件必须仍与记录中的修改后内容和属性一致；备份必须与原摘要一致，状态文件必须明确标记原先存在或缺失。符号链接路径、非普通文件和多硬链接文件拒绝恢复。每个文件写入前再次核对；写入后检查完整摘要或原先缺失状态，再通过独立 SSH 命令回读。只有独立回读通过才把历史标记为已恢复。

历史记录缺少修改后文件证据时，仍可加载和查看，原摘要及序列化格式保持兼容，但不能授权自动覆盖。操作者需要保留备份，核对完整当前文件与业务变化，再通过对应实例的修补流程规划恢复；不能推测旧记录之后无人修改文件，也不能凭配置项相同补造证据。

## 结果与失败

- 恢复结果说明已核对完整文件，不宣称运行配置或业务健康已恢复。Redis/Nginx 候选解析规则的变化不会再使完整文件恢复因标量比较不同而失败。
- 独立回读失败或断连时保留备份和失败日志，不再自动把旧基线值重新写回。尚未通过验证的恢复不能标成已恢复；须核对目标实际状态后再处理。
- 当前 core 仍保留原计划中适用的配置验证与 SSH/sysctl 重载策略。Redis 候选恢复不新增通用修改权限，也不猜测 Redis 重启命令。

Shell 中的重复检查不是原子文件事务，仍存在检查与写入之间的并发窗口；多文件中途 I/O 失败、断电和运行中的敌对进程持续替换路径，不在已保证的恢复范围内。要开放生产界面仍需接通完整预览、确认和失效管理，并补足受控文件描述符/事务恢复、并发写入、服务运行状态和各平台真实矩阵。复制使用原备份属性，当前独立回读结论限定为完整内容摘要或缺失状态。

## 真实实验入口

```powershell
cargo test --locked --package lovelyhawk-core baseline::
cargo build --locked --package lovelyhawk-backend --bin lovelyhawk-backend
node tools/lab/probe-baseline-restore.mjs
```

探针创建独有 Redis 镜像容器，核对 ID、镜像摘要、标签、网络及挂载；限制 256 MiB、1 CPU、128 个进程，`/data` 为受限 tmpfs，没有宿主目录挂载或特权。Rust 实验再次核对 SSH 目标中的本次随机标记，通过实际服务的计划、确认、执行、日志和独立验证运行，不新增测试专用 RPC，也不导入用户连接库。

SSH 基线记录由实际变更服务生成；Redis 恢复样例由实验明确构造修改前后文件及完整证据，用于验证候选规则兼容、备份校验和恢复行为，不代表产品已支持 Redis 自动修补。后续内容、权限与 inode 变化、损坏备份、符号链接替换、原先缺失文件，以及执行与回读之间的干预均作为负例。报告和失败材料保存在 `target/lab-baseline-restore/<runId>/`；仅清理本次容器和独立应用数据。

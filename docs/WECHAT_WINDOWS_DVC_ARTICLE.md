# 只开 3389 也能做深度应急？揭秘 LovelyHawk 基于 RDP DVC 的 Windows 远程取证技术

## 导读

在真实的 Windows 应急响应现场，防守方最常遇到的窘境是：防火墙策略极其严格，目标服务器**仅开放了 TCP 3389（RDP）端口**，没有 WinRM、没有 SSH、不通 SMB，更不允许提前部署厚重的常驻 Agent。传统的做法往往只能连上远程桌面，在狭小的窗口里手动打开任务管理器、事件查看器或敲 PowerShell，排查效率低、证据难留存。

在开发 **LovelyHawk** 的 Windows 应急响应工作台时，我们引入了微软官方底层协议特性——**RDP 动态虚拟通道（Dynamic Virtual Channel, DVC）**，直接复用已有的 3389 远程桌面连接，在本地工作台与远程会话之间建立了一条结构化、双向校验的取证通道。本文将为您深度拆解 DVC 的底层协议机制，以及它在 LovelyHawk 中的完整工程实践。

---

## 被锁死的 3389 边界：传统远程桌面排查困在哪里？

在应急响应与安全排查中，到达现场的第一步往往是“连上去”。面对一台处在隔离区或严格内网边界下的疑似失陷 Windows 服务器，传统方式通常会撞上三道墙：

- **网络边界严苛**：安全域或主机防火墙只放行了 `TCP 3389`，无法通过 WinRM（5985/5986）、SMB（445）或额外端口下发排查任务。
- **剪贴板与磁盘映射高危且脆弱**：RDP 的磁盘重定向（`rdpdr`）和剪贴板重定向（`cliprdr`）不仅传输大文件慢、容易卡死远程桌面 UI，而且双向挂载本地磁盘极易被失陷主机上的恶意代码反向利用，甚至污染取证人员的分析机。
- **纯图形界面操作效率低、难留证**：在远程桌面里人工翻看几万条安全日志、比对进程父子关系、逐个展开注册表 `Run` 键，既耗时又容易遗漏关键线索，更无法自动完成跨模块关联与全链路 SHA-256 校验。

这也引出了我们在设计 LovelyHawk 时的核心问题：**能不能在不开放任何新端口、不改变目标网络配置、不挂载本地磁盘的前提下，让本地取证工作台直接与远程桌面会话进行结构化“对话”？**

答案就藏在 RDP 协议栈自带的 **DVC（Dynamic Virtual Channel，动态虚拟通道）** 之中。

## 剥开 RDP 协议栈：藏在画面流底下的 DRDYNVC 动态虚拟通道

很多人把 RDP（远程桌面协议）看作单纯传输屏幕位图和键鼠事件的图片流协议，但实际上，RDP 在传输层（TCP 3389）与 MCS（T.125 多点通信服务）之上，设计了一套完整的**虚拟通道多路复用体系**。

从协议演进来看，RDP 的虚拟通道分为两代：

- **静态虚拟通道（SVC, Static Virtual Channel）**：RDP 早期引入的扩展机制。剪贴板（`cliprdr`）、音频（`rdpsnd`）、设备重定向（`rdpdr`）本质上都是静态虚拟通道。但 SVC 有着严格的协议限制：通道名称最长仅允许 **8 个 ASCII 字符**，单次连接最多只能建立 **31 条**静态通道，且必须在 RDP 握手初期一次性协商完毕，中途无法按需增删，一旦某条大流量通道拥塞还容易拖慢整个会话。
- **动态虚拟通道（DVC, Dynamic Virtual Channel）**：自 Windows Vista / Windows Server 2008（RDP 6.0+）起，微软在 `[MS-RDPEDYC]` 规范中正式引入了 DVC。它并没有推翻原有的通道模型，而是巧妙地**将一条名为 `DRDYNVC` 的静态虚拟通道作为“多路复用隧道总线”**。

```text
+-----------------------------------------------------------------------+
|                        应用层：LovelyHawk 取证协议                    |
|     [4字节小端长度前缀] + [JSON 控制帧 / 48KiB 文件分块 + SHA256]     |
+-----------------------------------------------------------------------+
|            动态虚拟通道层 (DVC)：dvc::lovelyhawk::winir               |
|   DYNVC_CREATE_REQ/RSP | DYNVC_DATA_FIRST | DYNVC_DATA | DYNVC_CLOSE  |
+-----------------------------------------------------------------------+
|          静态虚拟通道层 (SVC)：DRDYNVC (动态虚拟通道多路复用器)       |
|            与其他静态通道 (rdpdr / cliprdr / rdpsnd) 并行传输         |
+-----------------------------------------------------------------------+
|                RDP 传输底座：MCS (T.125) / X.224 / TLS                |
|                         单一 TCP 3389 连接                            |
+-----------------------------------------------------------------------+
```

在 `DRDYNVC` 通道内部，RDP 客户端与远程桌面服务（`TermService`）通过一套轻量级控制 PDU 来管理子通道的生命周期：

1. **按需动态建连（`DYNVC_CREATE_REQ` / `RSP`）**：远程会话内的进程可以在 RDP 登录后的**任意时刻**请求打开一条以长字符串命名的通道（例如 `dvc::lovelyhawk::winir`）。`TermService` 会通过 `DRDYNVC` 向客户端发送携带通道名称与动态 `ChannelId` 的创建请求；客户端插件同意后返回 `DYNVC_CREATE_RSP`，一条独立的双向管道即刻生效。
2. **大数据分片与优先级隔离（`DYNVC_DATA_FIRST` / `DYNVC_DATA`）**：当应用层发送超出单个 RDP PDU 容量的消息时，DVC 层会首包发送携带总长度的 `DYNVC_DATA_FIRST`，后续分片发送 `DYNVC_DATA`，与屏幕图形渲染帧互不干扰。
3. **独立销毁与重连（`DYNVC_CLOSE`）**：远程采集程序退出或重启时，仅销毁对应的 `ChannelId`，完全不影响当前正在操作的远程桌面图形会话。

## 告别 DLL 注入与管理员提权：Rust 进程内 COM LocalServer 架构

要在本地接管 `mstsc.exe` 的 DVC 流量，必须实现微软定义的四个核心 COM 接口：`IWTSPlugin`、`IWTSListenerCallback`、`IWTSVirtualChannelCallback` 和 `IWTSVirtualChannel`。

在传统的 C/C++ 实现中，开发者通常将插件编译为一个 `InprocServer32` 的 DLL，注册到系统 `HKLM` 下让 `mstsc.exe` 加载进自身进程空间，然后再自己写一套命名管道（Named Pipe）或共享内存 IPC 把数据转发给主界面程序。这种方案不仅链路冗长、容易因 32/64 位宿主差异崩溃，而且写 `HKLM` 注册表必须要求本地管理员权限。

在 LovelyHawk 中，我们使用 **Rust + `windows-rs`** 构建了一套更轻量、零提权的 **进程外 COM LocalServer（Out-of-Process COM Server）** 架构：

```text
[本地分析机：LovelyHawk 工作台]                [被检服务器：远程 RDP 会话]
+---------------------------------+          +---------------------------------+
| LovelyHawk 主进程 (Rust)        |          | 免落地 PowerShell 内存脚本      |
|   ├─ 内置 COM LocalServer 线程  |          |   或 lovelyhawk-win-agent.exe   |
|   │   (IClassFactory/IWTSPlugin)|          |                                 |
|   └─ IGlobalInterfaceTable 解封 |          |                                 |
+---------------------------------+          +---------------------------------+
                 ▲                                            ▲
                 │ 本地 DCOM/RPC 跨进程回调                    │ Win32 WTS API
                 ▼                                            ▼
+---------------------------------+  TCP 3389 +---------------------------------+
| 系统自带 mstsc.exe (RDP 客户端) | <=======> | Windows 远程桌面服务 (TermService)|
|   └─ 读取 HKCU AddIns 加载插件  |  dvc::    |   └─ WTSVirtualChannelOpenEx   |
+---------------------------------+  lovelyhawk+---------------------------------+
                                     ::winir
```

### 仅需当前用户权限的 HKCU 注册

`mstsc.exe` 在启动枚举插件时，除了读取系统级 `HKLM` 外，同样支持读取当前用户的 `HKCU` 注册表。LovelyHawk 将插件 CLSID 与 AddIn 统一登记在当前用户空间下：

- `HKCU\Software\Classes\CLSID\{D9B80669-C06A-4BD1-9CB1-3B7168C9E3A3}\LocalServer32`
- `HKCU\Software\Microsoft\Terminal Server Client\Default\AddIns\SimpleRdpPlugin`

这意味着**分析人员在本机无需管理员提权**，点击一次按钮即可完成插件注册或清理。

### 主进程直接承载 COM 服务与跨 Apartment 安全写入

当 `mstsc.exe` 启动并发现该 `LocalServer32` 注册项时，Windows COM 子系统会通过 `CoRegisterClassObject` 直接连接到正在运行的 LovelyHawk 主进程：

- LovelyHawk 在独立的后台 MTA 线程中初始化 COM 并运行消息循环，直接向 `mstsc.exe` 暴露 `IWTSPlugin` 实例并监听 `dvc::lovelyhawk::winir` 通道。
- **攻克 COM 跨线程封送难题**：COM 接口指针具有严格的线程套间（Apartment）亲和性，`OnNewChannelConnection` 回调交给我们的是绑定在回调套间上的 `IWTSVirtualChannel` 代理指针，如果直接拿到 Rust 的异步工作线程里调用 `Write` 会触发 `RPC_E_WRONG_THREAD` 或死锁。为此，LovelyHawk 引入了 Windows 原生的 **`IGlobalInterfaceTable`（全局接口表，GIT）**：在通道建立瞬间将接口登记为全局 Cookie，任何 Rust 工作线程在发送取证指令时，先通过 Cookie 解封出当前线程合法的代理指针再执行写入，实现了零中间 IPC 进程的丝滑通信。

## 三步建立取证链路：从免落地内存加载到原生采集端

底层的 COM 协商被完全封装在工作台内部。反映到用户界面上，安全工程师只需要按照接入向导完成三个动作：

1. **注册插件并启动监听**：工作台在当前用户注册表登记插件，并在进程内拉起 COM LocalServer 监听。
2. **打开远程桌面连接服务器**：既可以唤起系统 `mstsc.exe`，也可以使用工作台内置的原生远程桌面视图（通过进程句柄与 `TscShellContainerClass` 双重校验嵌入，默认采用 `/public` 模式、关闭磁盘与打印机重定向，临时 `.rdp` 配置文件不含密码且断开即焚）。
3. **在远程会话中启动采集端（提供两种形态）**：
   - **免落地 PowerShell 脚本（零文件落盘）**：针对不便投放二进制文件的高敏环境，工作台动态生成一条纯 ASCII 的 `powershell.exe -EncodedCommand` 单行命令（内部采用 UTF-16LE Base64 编码，彻底规避远程桌面粘贴多行脚本时因换行、花括号或输入法导致的截断）。脚本在内存中通过 `Add-Type` 即时编译一小段 C# P/Invoke 代码，直接调用系统 `wtsapi32.dll` 打开 DVC 通道，不修改系统 ExecutionPolicy，也不关闭任何安全防护。
   - **独立原生采集端（`lovelyhawk-win-agent.exe`）**：由纯 Rust 编译的无 GUI 单文件程序，无第三方运行时依赖，不注册服务、不写自启动项，复制到远程桌面双击或命令行运行即可接通。

## 拆解 DVC 字节流：PDU 分片重组、流式分帧与 WTS API 的“深坑”

当你真正使用 Win32 API 编写远程会话内的 DVC 采集端时，就会发现客户端收发与服务端收发在字节层面上并不是对称的——这也是许多简易 Demo 一传真实取证数据就崩溃的原因。

### 底层 PDU 重组与应用层流式分帧

在客户端（LovelyHawk 主进程），`IWTSVirtualChannelCallback::OnDataReceived` 收到的是 `mstsc.exe` 已经剥离了底层头的纯载荷流；但在远程服务端（被检主机），调用 `WTSVirtualChannelRead` 每次读出的缓冲区最前面，都会被系统强制附带一个 **8 字节的 `CHANNEL_PDU_HEADER`**：

```text
+------------------------+------------------------+-------------------------------+
|  total_length (4 字节) |     flags (4 字节)     |      当前分片载荷 (Payload)   |
|     u32 Little-Endian  | 0x01=FIRST | 0x02=LAST |       典型单次约 1600 字节    |
+------------------------+------------------------+-------------------------------+
```

如果一条指令或脚本体积超过约 1,600 字节，Windows 远程桌面服务会将其拆成多个 PDU 分片。为此，LovelyHawk 在 `lovelyhawk-win-dvc` 中设计了双层流式状态机：

- **第一层：`PduReassembler`（PDU 分片重组器）**：服务端每次从 `WTSVirtualChannelRead` 读取后，先解析前 8 字节头，遇到 `CHANNEL_FLAG_FIRST (0x01)` 重置重组缓冲区，持续拼接中间分片，直到捕获 `CHANNEL_FLAG_LAST (0x02)` 才向上层交付完整字节块，并严格限制单帧最大 16 MiB，防止恶意或损坏数据造成内存耗尽。
- **第二层：`StreamDecoder`（长度前缀流式解码器）**：在完整字节流之上，采用 `[4 字节小端长度 u32] + [UTF-8 JSON 帧]` 进行应用层封帧，统一承载指令下发（`cmd`）、结构化采集结果（`result`）、交互消息（`chat`）以及文件分块流（`file_start` / `file_chunk` / `file_end`）。

### 踩坑实录：那些文档没写透的 WTS 运行时细节

在真实 Windows 环境打磨 DVC 通道的过程中，我们解决了几个极具隐蔽性的工程问题：

- **`WTSVirtualChannelRead` 的“零字节成功”不是断连**：在常规 Socket 或文件编程中，`read() == 0` 代表对端关闭连接（EOF）。但在 Windows WTS 虚拟通道中，当通道处于空闲状态时，`WTSVirtualChannelRead` 往往会返回 `TRUE` 且 `bytesRead == 0`，或者返回 `FALSE` 并置 `GetLastError()` 为 `ERROR_TIMEOUT (1460)` / `ERROR_IO_INCOMPLETE (996)`。如果将其误判为 EOF，采集端就会在空闲几秒后频繁断开重连。LovelyHawk 专门实现了空闲轮询判定（`read_is_idle`），只有遇到真正的句柄失效或会话关闭才进入 1–30 秒指数退避重连。
- **句柄生命周期与并发写保护**：当远程会话闪断重连时，如果上一条采集指令的后台线程刚刚执行完，极易把结果写进已经关闭或被操作系统复用的 `HANDLE` 中。我们在 Agent 内置了写锁与 `AtomicBool` 停止栅栏，通道关闭与写入严格互斥，且重连后绝不自动重放不知状态的旧指令。
- **断线重连后的主机身份核验**：每次 DVC 通道建立都会生成全新的 `session_id` 防止跨会话串台。而当网络抖动导致通道重连时，工作台会自动核对远程主机的**主机名、域/工作组与系统版本**：确认仍是同一台被检主机时，自动保留重连前已采集的各模块快照与选中状态；若发现切换到了另一台主机，则立即清空旧快照，兼顾现场排查的连续性与证据隔离。

## 实战演练：沿着一条 DVC 通道揪出隐藏驻留木马

当 DVC 通道接通后，LovelyHawk 左侧导航栏将 Windows 应急响应清晰划分为 **研判、排查、取证、连接** 四大工作域、共十个功能视图。分析人员无需再切回拥挤的远程桌面里手敲命令，即可完成从发现异常到提取样本的完整闭环。

以对目标主机 `WIN-ATIGDETTLA3` 的一次真实排查为例：

### 第一步：启动项排查与跨模块自动关联

在 **「排查 → 启动项」** 模块中，工作台通过 DVC 通道一次性聚合了注册表 `Run/RunOnce`、各用户及系统的启动文件夹、计划任务与服务持久化项，并按风险等级自动打标。

如下图所示，我们在 11 个启动项中一眼锁定了 6 条被标为 **「中危」** 的异常记录 `WindowsUpdateHelper`——它伪装成系统更新组件，实际指向 `AppData\Roaming\Microsoft\Windows\Update\sysguard.exe`：

![[Pasted image 20261025172031.png]]

更关键的是右侧详情面板底部的 **「关联线索」**：LovelyHawk 并没有把各个模块做成孤立的表格，而是自动将当前选中的启动项与已采集的 **进程分析**、**启动项** 进行交叉比对，直接提示当前有 3 个正在运行的 `sysguard.exe` 进程（PID `1988`、`4220`、`5100`），并严谨地区分了哪些是 **「完整路径相同」**、哪些是 **「仅文件名相同」**，帮分析人员瞬间串起“持久化注册表项 → 落地目录 → 活跃进程 PID”的证据链。

### 第二步：远程文件取证与样本无损拉取

顺着启动项暴露出的可疑路径，我们直接切换到 **「取证 → 文件排查」** 模块，像操作本地资源管理器一样定位到 `C:\Windows\system32\config\systemprofile\AppData\Roaming\Microsoft\Windows\Update` 目录：

![[Pasted image 20261025172059.png]]

在这里可以清晰看到，攻击者将 `config.json`、`sysguard.exe`（143 KB）和 `sysupdate.exe`（143 KB）全部加上了 **「隐藏 + 系统」** 属性以躲避常规目录查看。在右侧取证面板中，我们可以：

- 直接点击 **「预览前 16 KB」** 查看配置文件内容或可执行文件的十六进制与 PE 头信息；
- 点击 **「取证拉取 (≤ 8 MB)」**，通过 DVC 通道将远端的 `sysguard.exe` 或 `config.json` 按 **48 KiB 分块**流式传输回本地工作台。

## 克制而诚实的工程边界：不给应急现场添乱

在应急响应工具的设计上，“不添乱、不越界、证据可信”远比“功能炫酷”更重要。LovelyHawk 的 Windows DVC 模块在底层执行与证据处理上划定了三条铁律：

- **子进程非阻塞排空与防卡死机制**：在远程主机上调用系统命令或查询脚本时，最怕遇到子进程挂起，或者派生的孙进程继承了 `stdout/stderr` 管道句柄迟迟不退出，导致采集端永久阻塞。LovelyHawk 在原生采集端中使用 `PeekNamedPipe` 非阻塞轮询配合双线程并发排空管道，严格限制单次采集超时（35 秒）与输出体积上限（2 MiB），一旦超时立即终止等待并回收读取线程。
- **端到端 SHA-256 证据完整性闭环**：通过 DVC 拉取远端样本时，读取期间一旦发现文件大小发生变动立即报错中止；传输过程按 48 KiB 分块流式计算哈希；工作台接收完成时核对一次 SHA-256，操作员通过宿主原生对话框另存到本地磁盘时再次核对 SHA-256，且强制只创建新文件、绝不覆盖本地已有文件。
- **坚持“诚实报告”原则**：没有相应组件、权限不足、通道不可读或记录达到上限截断时，界面会独立显示采集缺口与警告说明；即使远程连接中途断开，也会如上面截图所示保留旧快照供离线研判并明确提示“连接已断开，旧快照仅供查看”，**绝不把“无权限读取”或“未核查”粉饰成“0 风险 / 安全通过”**。
